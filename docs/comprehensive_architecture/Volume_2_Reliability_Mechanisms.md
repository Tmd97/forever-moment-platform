# Forever Moment Platform/Core Service - Volume 2: Reliability Mechanisms

## SECTION 5 - REQUEST IDEMPOTENCY DESIGN

### REQUEST IDEMPOTENCY IMPLEMENTATION

#### PART A - PROBLEM BEFORE IMPLEMENTATION
Before the introduction of strict request idempotency, the system suffered from several distributed systems anti-patterns:
1. **User Double-Clicking Book Button:** A user clicks "Book Now". The UI freezes for 500ms. The user clicks again. Two concurrent HTTP POST requests reach the API gateway. Because Postgres allows concurrent inserts if capacity permits, two `BookingReservation` records were created, and two Kafka events were dispatched. Result: Customer is billed twice.
2. **Browser / Mobile Network Retry:** The user clicks "Book Now". The transaction completes in Postgres. The API starts returning the HTTP 201 response, but the user's mobile connection drops (e.g., entering a tunnel). The mobile OS TCP stack reports a failure. The App automatically retries the identical payload. Result: Duplicate booking.
3. **API Gateway Retry:** If the Platform service pauses for a JVM Garbage Collection (GC) for 5 seconds, the API Gateway might timeout the request and automatically route it to Platform Instance 2. Instance 1 finishes and commits. Instance 2 executes the same request. Result: Duplicate booking.
4. **Service Restart During Request:** The pod is killed via SIGTERM while executing. The client gets a 502 Bad Gateway and retries. If the pod was killed *after* the DB commit, the retry causes a duplicate.

**Data Corruption Scenarios:**
- Inventory `booked_count` exceeds actual distinct customers.
- The Payment Service processes multiple charges for one customer intent.
- Downstream CRMs create multiple identical profiles.

#### PART B - IMPLEMENTATION DETAILS
To solve this, the Platform uses a strict Idempotency Key approach driven by `BookingRequestIdempotencyCoordinator`.

- **Idempotency Key:** A V4 UUID generated by the *client* (e.g., frontend app). It represents the user's *intent* to book.
- **Fingerprint:** A SHA-256 hash of the sanitized request payload. *Why?* If a user sends Key A with "Pax: 2", fails, and retries Key A with "Pax: 4", we must reject it. The fingerprint ensures the key is permanently bound to the original payload.
- **Ownership Token:** During execution, the request is marked `IN_PROGRESS`. This acts as a distributed Mutex lock preventing concurrent threads from executing the same key.
- **Lease Expiration:** `lease_expiration` column. If a pod crashes while holding an `IN_PROGRESS` lock, it will never mark it `COMPLETED`. The lease expires after exactly 2 minutes, allowing a subsequent retry to take ownership.
- **Request States:** 
  - `IN_PROGRESS`: Executing right now.
  - `COMPLETED`: Successfully committed to DB. Response cached.
  - `FAILED`: Execution failed (e.g., Bad Request, DB offline). Safely retriable.

#### PART C - DATABASE DESIGN
**Table:** `booking_request_idempotency`

| Column | Type | Constraints | Purpose |
| :--- | :--- | :--- | :--- |
| `idempotency_key` | VARCHAR(255) | PRIMARY KEY | The UUID from the client header. Fast indexed lookup. |
| `fingerprint` | VARCHAR(255) | NOT NULL | SHA-256 string to detect payload tampering on retries. |
| `state` | VARCHAR(50) | NOT NULL | Tracks lifecycle (IN_PROGRESS, COMPLETED, FAILED). |
| `response_payload` | JSONB | NULLABLE | Stores the exact JSON string returned to the client on success. Used for fast replays. |
| `lease_expiration` | TIMESTAMP | NOT NULL | Failsafe mechanism for pod crashes. |
| `created_at` | TIMESTAMP | NOT NULL | Audit. |
| `updated_at` | TIMESTAMP | NOT NULL | Audit. |

*Why this design?* The Primary Key acts as the ultimate concurrency guard. `INSERT ... ON CONFLICT DO NOTHING` guarantees exactly one thread creates the `IN_PROGRESS` row.

#### PART D - RACE CONDITIONS PREVENTED
**Timeline of a prevented race condition:**
- `T=0`: Request 1 (Instance A) and Request 2 (Instance B) arrive with Key `uuid-1234`.
- `T=1`: Both instances call `idempotencyDao.insertIfAbsent(uuid-1234)`.
- `T=2`: PostgreSQL serializes the inserts. Instance A wins. Row is inserted with `IN_PROGRESS`.
- `T=3`: Instance B's insert fails (Duplicate Key violation caught by `ON CONFLICT DO NOTHING` logic).
- `T=4`: Instance B does a `SELECT` on `uuid-1234`. It sees `IN_PROGRESS`.
- `T=5`: Instance B throws `IdempotencyLockedException` (HTTP 423 Locked) to the client.
- `T=6`: Instance A completes the booking, updates state to `COMPLETED`, and saves the response.
- `T=7`: Client receives 423 Locked and auto-retries 1 second later.
- `T=8`: Request 3 arrives. Database shows `COMPLETED`. Instance retrieves `response_payload` and returns HTTP 200 OK.

#### PART E - BEFORE VS AFTER
**Before Idempotency:**
`Client -> POST -> Service -> Postgres Insert -> Return`
(Network fails, Client Retries) -> `Client -> POST -> Service -> Postgres Insert (DUPLICATE) -> Return`

**After Idempotency:**
`Client -> POST (Key X) -> Service -> Save Idempotency(Key X) -> Postgres Insert -> Return`
(Network fails, Client Retries) -> `Client -> POST (Key X) -> Service -> Detect Key X (COMPLETED) -> Return Cached Response` (Zero DB side effects).

## SECTION 6 - OUTBOX PATTERN

### RELIABLE EVENT PUBLISHING ARCHITECTURE

#### 1. Why Outbox Exists
A microservice cannot atomically commit a Postgres transaction and send a Kafka message. If the DB commits, but the Kafka `producer.send()` fails (broker timeout, DNS failure), the platform has booked the inventory, but the Booking/Payment service will *never* know about it. The customer shows up at the venue, but they haven't paid, and no official booking ticket was emailed.

#### 2. Failure Scenarios without Outbox
- **DB Commit Success -> Kafka Publish Failure:** Data inconsistency. Booking exists locally, invisible globally.
- **Kafka Publish Success -> DB Commit Failure:** Even worse. The event is fired, user is billed, but the Platform rolled back the transaction. The booking doesn't exist locally, but money was taken.

#### 3. How Outbox Solves It
We use a Transactional Outbox. 
Inside `BookingCreationTransactionService`, we write the `BookingReservation` and a `BookingOutbox` record inside the *exact same `@Transactional` block*.
If the database commits, we are 100% guaranteed to have an outbox record. If the database rolls back, we have no reservation and no outbox record.

Once committed, a separate process (Async thread or Quartz job) reads the Outbox table and publishes to Kafka. Once Kafka acknowledges (ACK), the outbox row is updated to `PUBLISHED`.

#### 4. Documenting Outbox Database
**Table:** `booking_outbox`
- `id` (UUID): Primary Key.
- `payload` (JSONB): The exact serialized JSON representation of the `BookingCreatedEvent`.
- `status` (VARCHAR): `PENDING`, `PUBLISHED`, `FAILED`.
- `owner_node` (VARCHAR): Identifies which Quartz worker is currently handling this row.
- `lease_expires` (TIMESTAMP): When the owner_node loses its lock.
- `retry_count` (INT): How many times we tried to send to Kafka.

## SECTION 7 - QUARTZ RETRY ARCHITECTURE

#### 1. Why Quartz Exists
Direct Kafka publishing via the Fast-Path (`BookingEnrichmentTask`) is great for latency. It runs immediately after the DB commits. However, if the JVM crashes 1 millisecond after the DB commits, the Fast-Path thread dies. The event is stuck in the DB Outbox as `PENDING`. 

`OutboxRetriesJob` (a Quartz Scheduler Job) exists purely as a sweeper/recovery mechanism.

#### 2. Polling Logic
Quartz triggers every 1 minute.
It runs: `SELECT * FROM booking_outbox WHERE status = 'PENDING' AND (lease_expires IS NULL OR lease_expires < NOW())`.

#### 3. Retry Lifecycle
- **Step 1:** Quartz queries PENDING records.
- **Step 2:** It claims a batch of records (max 50) using Atomic Claims (see Section 8).
- **Step 3:** For each record, it deserializes the payload, connects to Kafka, and invokes `producer.send()`.
- **Step 4:** Upon successful ACK, it updates the record status to `COMPLETED`.
- **Step 5:** If Kafka throws an exception, it increments `retry_count`. If `retry_count > 5`, it marks it as `FAILED`.

#### 4. Application Crash Scenarios Handled
- **DB Outage:** Quartz halts. When DB recovers, Quartz resumes picking up `PENDING` records.
- **Kafka Outage:** Fast-path fails and logs warning. Quartz picks it up, fails, increments retry count. This repeats until Kafka returns or `retry_count` hits limit.
- **Publish Success but Status Update Failure:** If Kafka receives it, but Quartz crashes before updating `status = COMPLETED`, Quartz will retry the publish later. This causes a *Duplicate Event* on Kafka. This is accepted behavior ("At-Least-Once" delivery). Consumers downstream *must* be idempotent.

## SECTION 8 - ATOMIC CLAIMS IMPLEMENTATION

#### Problem Before Atomic Claims
Since Quartz runs in a clustered mode or we have multiple Pods polling the outbox, two workers might execute `SELECT * FROM outbox WHERE status = 'PENDING'` simultaneously. Both retrieve Event X. Both send Event X to Kafka. We just flooded the broker with duplicates.

#### The Implementation
We implemented a strict "Pessimistic Locking / Claim" pattern using atomic SQL updates via `BookingOutboxDaoImpl`.

#### Claim Ownership Flow
1. **Node Identification:** Every JVM instance generates a unique UUID on startup (`owner_node_id`).
2. **Atomic SQL Update:**
   ```sql
   UPDATE booking_outbox 
   SET owner_node = 'node-xyz', lease_expires = NOW() + INTERVAL '30 seconds' 
   WHERE status = 'PENDING' 
     AND (owner_node IS NULL OR lease_expires < NOW())
     AND id IN (select top 50 ids...);
   ```
   PostgreSQL guarantees this update is atomic. Only one node will successfully set its `owner_node`.
3. **Select Claimed:** The node then runs `SELECT * FROM booking_outbox WHERE owner_node = 'node-xyz'`.
4. **Execution:** The node safely processes these records knowing no other node will touch them for 30 seconds.

#### Lease Expiration and Recovery
If `node-xyz` encounters a fatal OutOfMemoryError and dies while processing, it never clears the `owner_node` flag. However, the `lease_expires` timestamp acts as a dead-man's switch. 30 seconds later, another node's atomic SQL update will override the dead node's claim and recover the stuck events.

**Timeline Example:**
- `T=0`: Pod A updates row 1, setting `lease_expires = T+30`.
- `T=1`: Pod A crashes.
- `T=15`: Pod B polls, ignores row 1 because `lease_expires` is still in the future.
- `T=31`: Pod B polls, condition `lease_expires < NOW()` matches. Pod B claims row 1.
- `T=32`: Pod B publishes row 1 to Kafka. Fault tolerance achieved.
